Which Pages to Fix First? Sorting Content Into Archetypes for Search Triage

Heba Walid Awad · Structured Content Archetype Clustering lane
Abstract. Out of thousands of published pages, which ones deserve a human editor's attention first? I grouped 30,000 pseudonymized FlyRank pages into simple performance archetypes using K-Means clustering, validated on pages from clients the model never saw during fitting. Against a transparent, hand-written tier rule on the same held-out clients, the clustering found noticeably clearer groupings (silhouette 0.84 vs. −0.13). I then applied a plain staleness-and-CTR rule on top of the archetypes to produce a ranked, reason-coded queue: about 12% of pages are flagged refresh (stale and underperforming), 16% investigate (underperforming but not stale — likely not a staleness problem), and the rest monitor. This is a decision-support tool for weekly editorial triage, not a prediction of future traffic or a causal claim about what refreshing a page will do.

Introduction

FlyRank researches, writes, and publishes content into client websites, then watches search performance and optimizes. A recurring, unglamorous decision sits behind that loop: with limited editor time, which pages get reviewed this week? FlyRank's product already flags pages with hand-written rules — a health score, quick-win tags — but rules run out where signals get numerous and tangled. This project asks whether a simple learned grouping of pages can sharpen that same decision without pretending to know more than the data supports.

Data

I used the FlyRank internship starter release, content_refresh_anonymized.csv — 30,000 pseudonymized content items across 32 clients, aggregated over a trailing 90-day window ending at export time. This is a single snapshot, not a time series.

Deliberately excluded from every feature, score, or cluster input:

  • trend_direction / trend_pct — these define the growth/decline label; using them as inputs would be circular, not a finding.
  • content_id / client_id — pseudonymous identifiers, used only to build a grouped train/test split, never as model inputs.
  • Any FlyRank product flag (health score, priority score) — these encode a decision someone already made, and using them as inputs would just reproduce that decision.

No client names, domains, raw search queries, or credentials appear anywhere in this project's repository or outputs.

Methodology

Method: K-Means clustering on two features — 90-day impressions and days since last update — kept deliberately small so every grouping is explainable in one sentence. There is no outcome label to predict here; the question is "what shapes exist in this data," not "what will happen next."

Split: pages from the same client share templates and editorial habits, so a random row split would let the model look better than it generalizes. I held out 20% of clients entirely — the model never saw their pages while fitting — and evaluated only on that held-out set.

Baseline: a transparent, hand-written tier-cross rule (freshness tier × impression tier), the same "if-statement" logic FlyRank's product already runs in production. No fitted parameters — the bar any learned model has to clear.

Leakage check: the feature list contains only impressions_90d and days_since_last_update — no label-derived, product-derived, or identifier columns are used anywhere in the clustering step.

Results

On the same held-out clients, K-Means produced substantially better-separated groups than the baseline rule:

MethodGroupsSilhouette (held-out clients)
Baseline tier rule14−0.13
K-Means archetypes40.84

Worth noting for fairness: the baseline rule produces 14 fine-grained tiers by construction, while K-Means was asked for 4 broader groups — part of the gap is that the baseline is simply more fragmented, not only that it's a worse fit. A K-Means run forced to also produce ~14 clusters would likely close some of this gap. The honest takeaway is directional: a small number of learned groups separates this data at least as cleanly as a much larger set of hand-written tiers, which is a useful property for a human trying to keep a handful of archetypes in their head.

Limitations & Honest Framing

  • No causal claim. Archetype membership and the refresh flag are a same-snapshot comparison. Nothing here shows that refreshing a page causes its CTR to improve — no refresh was actually run and measured in this dataset.
  • One snapshot, not a trend. The 90-day window is a photo, not a video — it says nothing about a page's trajectory before or after it.
  • Modest, not sharp, separation. A silhouette of 0.84 with only 2 simple features indicates real structure but should not be read as proof of "true" content archetypes — it's a useful lens, not a hard boundary.
  • Selection bias is unknown. Which pages FlyRank historically chose to refresh isn't in this dataset, so "refreshed pages later did better" cannot be tested here.
  • The model never reads the page. A flagged page could be a genuine problem, or a branded/navigational query where low CTR is normal — a human has to check before acting.

Ranked Recommendations

On top of the archetypes, a simple, transparent rule assigns each page one of three actions with a plain reason code:

  • refresh — stale (31+ days), still getting real traffic (500+ impressions/90d), and underperforming (CTR below the median of visible pages).
  • investigate — visible and underperforming, but not stale — likely not a staleness problem, needs a different kind of look before any content changes.
  • monitor — everything else: too little traffic to justify review time yet, or already performing fine.

How an editor would use this tomorrow: open the refresh tier first, sorted by traffic (biggest upside first). Before editing anything, confirm the query isn't branded/navigational, check for a recent ranking shake-up, and rule out a tracking gap for investigate pages. This queue is a starting point for a person's review, never an automated action.
